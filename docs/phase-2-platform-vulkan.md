# Phase 2 — Platform and Vulkan

## Exit scope

Phase 2 is complete only when the engine has cross-platform window/input integration, Vulkan initialization and device/queue selection, validation-layer support, presentation-capable queues and a complete swapchain lifecycle, explicitly owned GPU resource wrappers, reproducible shader compilation/reflection, and relevant automated tests. GPU-backed validation must run on suitable runners where available; unrun hardware tests must be identified rather than reported as passing.

## Implemented in the current Phase 2 branch

- Pinned workspace dependencies for ash 0.38.0, ash-window 0.13.0, raw-window-handle 0.6.2, and winit 0.30.13.
- Platform-native event-loop ownership through winit's ApplicationHandler lifecycle.
- Validated initial window configuration and a window-creation boundary that runs on the native event-loop thread.
- Normalized per-window keyboard and mouse state with held/pressed/released transitions, focus-loss release handling, cursor position, and accumulated wheel deltas.
- Centralized multi-window input routing with explicit registration, independent state, monotonic non-reused input-window identities, frame-boundary updates, and stale-window rejection.
- A reusable native-window manager that owns registered winit windows, maps native IDs to input identities, routes input events, and returns window ownership on removal.
- Window metrics for physical drawable extent, scale factor, focus, and minimized state.
- Surface-generation notifications on drawable-size and scale-factor changes, allowing renderer integrations to trigger swapchain recreation without a platform-to-renderer dependency.
- Event outcomes for close requests, redraw requests, focus transitions, and surface changes.
- Dynamic Vulkan loader discovery with actionable loader and API errors.
- Instance-extension and validation-layer discovery before instance creation.
- Optional Khronos validation layer and debug-utils callback; requested validation fails clearly if unavailable.
- The debug callback retains thread-safe validation diagnostics, exposed through `VulkanInstance::validation_messages()` for automated tests and runtime diagnostics. The lavapipe integration test exercises GLSL compilation/reflection, shader modules, graphics-pipeline creation, vertex-buffer upload/binding, a non-indexed draw, render-pass transitions, image-to-buffer copy, host visibility, and deterministic pixel readback.
- Vulkan portability enumeration is enabled when advertised; macOS initialization fails clearly if that extension is absent.
- Deterministic physical-device preference and graphics-queue-family selection.
- Portability-subset device extension enabled when advertised.
- Platform-required Vulkan instance extensions enumerated from the native display handle and validated before instance creation.
- Owned window surfaces with surface capability, format, present-mode, and queue-support queries.
- Physical-device selection requires both graphics and presentation support for a window surface and the swapchain device extension.
- Separate graphics and presentation queues are created when a single queue family cannot serve both roles.
- Explicit instance, debug-messenger, surface, swapchain, image-view, and logical-device destruction ownership.
- Swapchain selection for supported formats, color spaces, extents, image counts, composite-alpha modes, and FIFO/mailbox/immediate presentation preferences.
- Swapchain image views with deterministic destruction ordering; acquisition and presentation expose suboptimal/out-of-date states to the caller.
- Swapchain recreation waits for device idle and preserves the old swapchain for zero-size/minimized-window deferrals; failed nonzero recreation leaves a clear not-ready state that callers can retry.
- Explicitly owned Vulkan fence and binary-semaphore wrappers with device-borrowed lifetimes, structured API errors, fence timeout reporting, and device-idle waits only when destroying an unsignaled fence or semaphore.
- Explicitly owned Vulkan buffers with aligned suballocations from shared memory blocks, deterministic memory-type selection, required device-local or host-visible memory policies, upload/readback preference scoring, bounds-checked host access, and atom-aligned non-coherent cache maintenance. Host access does not implicitly wait for queues or insert memory barriers; callers own GPU/host synchronization, including synchronization for any atom-expanded cache range.
- Explicitly owned Vulkan images with compatible suballocations from shared device-memory blocks, device-local memory preference, validated dimensionality/mip/layer/sample configuration, and image views whose Rust lifetimes are bounded by their parent images. Image layout transitions, barriers, and queue ownership transfers remain caller/future-scheduler responsibilities.
- Explicitly owned Vulkan samplers with validated LOD ranges/bias, optional depth comparison, and device-limit-checked anisotropy. Logical-device creation enables sampler anisotropy only when supported; sampler ownership is device-borrowed and descriptor leases retain it through submission completion.
- Owned descriptor-set layouts and descriptor pools with validated bindings/capacities, device identity checks, and descriptor-set wrappers that borrow their pool and layout. Complete descriptor updates support uniform/storage buffers, sampled images, separate samplers, combined image samplers, and storage images. Updates validate descriptor binding/type/array slots, device identity, buffer usage/alignment/ranges, image usage/layout/aspects, and physical-device format features. Every slot must be written exactly once per batch. Resource leases retain buffers, image views, and samplers and prevent concurrent set updates; recorded submissions retain each lease until its fence signals. Queue synchronization, buffer barriers, and image layout transitions remain caller responsibilities.
- Owned Vulkan pipeline layouts that retain borrowed descriptor-set layouts, validate device identity, and validate push-constant stage masks, four-byte alignment, device size limits, overflow, and overlapping ranges for shared shader stages.
- GLSL 450 compilation uses the pinned shaderc/glslang source build and emits Vulkan 1.0 / SPIR-V 1.0 with optimization disabled. The compiler reflects uniform/storage buffers, sampled/storage images, separate/combined samplers, descriptor-array counts, push-constant sizes, and vertex input locations/formats; unsupported descriptor or vertex-input forms fail explicitly. A Vulkan shader-module wrapper owns the compiled module and retains the reflected interface. Compute pipeline creation validates descriptor types/counts/stages and push-constant coverage against the pipeline layout, then retains both shader module and layout. Owned render passes validate attachment/subpass references, dependencies, multisample resolves, and compatible sample counts. Owned framebuffers retain their render pass and image views, validate extents/layers/formats/usages/aspects, and check physical-device format features. Owned graphics pipelines validate vertex inputs, shader interfaces, subpass attachment counts, depth state, blend state, and fixed-function enums; viewport/scissor are dynamic, with fill rasterization as the initial supported mode. Resettable primary command pools/buffers are available on the selected graphics queue family. Recording scopes retain pipelines, layouts, render passes, framebuffers, buffers, images, and descriptor leases; unfinished recordings abort/reset on drop, abandoned executable buffers reset, and fence-backed submissions retain resources until completion. Resource wrappers destroy their Vulkan handles when their Rust borrows are released rather than forcing a device-wide idle; safe command recording and submission guards ensure those borrows outlive GPU use. Callers bypassing the safe wrappers through raw Vulkan handles own that synchronization contract. Recording supports render-pass/subpass transitions, graphics/compute pipeline binding, descriptor sets with dynamic-offset validation, push constants, dynamic viewport/scissor, vertex/index buffers, draw/indexed draw/dispatch, and buffer/image memory barriers. Buffer-to-buffer, buffer-to-image, image-to-buffer, and image-to-image copy commands validate usage, device identity, buffer alignment/bounds, image mip/layer/type/extent bounds, sample counts, and transfer layouts. Buffer-image copies support documented BC/ETC2/EAC/ASTC block formats and individual depth/stencil aspects with block-aware alignment and required-byte validation. Image-to-image copies remain limited to the documented uncompressed color-format set; unsupported formats/aspects return `UnsupportedCopyFormat`. Copy commands insert no implicit barriers, and queue-family ownership transfers are not exposed. Queue submission is serialized with presentation/device-idle operations and returns a waitable completion guard. The initial submission API handles one primary buffer on the graphics queue. Shaderc source builds require CMake 3.22.1 or newer and a C++17 compiler on each target platform. Buffers and images share aligned 16 MiB Vulkan memory blocks by compatible memory type; resources larger than a pool block receive a standalone allocation. Host-visible non-coherent buffer suballocations align to both Vulkan memory requirements and `nonCoherentAtomSize`, preventing cache-maintenance ranges from overlapping adjacent resources.
- A reusable frames-in-flight scheduler owns one initially-signaled fence and one image-acquired semaphore per frame slot, maps acquired swapchain images to their prior frame owners, waits prior owners before reuse, and resets a frame fence only after successful image acquisition. Presentation-completion semaphores are owned per swapchain image, not per frame slot, so a graphics fence is never mistaken for proof that presentation consumed its wait semaphore. Submission guards lease their frame slot until completion is acknowledged; timed-out frame waits do not reset fences, and out-of-date acquisition does not advance the frame ring.
- Acquired frame tickets bind the exact swapchain identity and must be submitted on the same device/swapchain. If a ticket is dropped before submission, the scheduler retains the acquisition and semaphore state so the same image can be resumed; replacing the swapchain while that acquisition remains pending is rejected. `FrameStart::Pending` asks the caller to release/wait the prior submission guard before retrying.
- Swapchain command recording tags executable command buffers with the exact swapchain owner/generation/image targeted by their swapchain framebuffer. The frame ticket rejects command buffers recorded for a different image or swapchain before resetting/submitting the frame fence.
- Swapchain-backed framebuffers now bridge swapchain image views into render-pass recording. The initial helper intentionally supports one single-sampled color attachment whose final layout is `PRESENT_SRC_KHR`; command recording retains the framebuffer and swapchain lifetime. More complex attachment sets (e.g. depth/MSAA resolve) remain caller-managed through separate framebuffer resources.
- Swapchain recreation passes the previous swapchain handle through Vulkan's `oldSwapchain` field, creates replacement resources before dropping the old owner, preserves the current swapchain for zero-size deferrals, and clears the owner after a failed nonzero recreation because Vulkan may already have retired the previous handle.
- Command recording now exposes buffer-to-buffer, buffer-to-image, image-to-buffer, and image-to-image copies. It validates transfer usage, device identity, 4-byte and texel-block buffer-offset alignment, checked buffer bounds, image mip/layer/type/extent bounds, sample/layout compatibility, and destination buffer overlap for buffer copies. Buffer-image transfers support documented BC/ETC2/EAC/ASTC block formats and individual depth/stencil aspects; image-to-image copies remain limited to documented uncompressed color formats. These operations do not insert barriers or perform queue-family ownership transfers; callers must establish layouts and memory dependencies.
- Device and swapchain teardown wait for outstanding device work before releasing owned resources. Individual resource retirement is tied to the command-submission fence and Rust borrow graph, avoiding device-wide idle waits on ordinary resource destruction.

## Frame scheduling contract

1. The platform layer owns minimized-window policy. Do not call `begin_frame` while the drawable extent is zero; retain the current swapchain until a nonzero extent is available.
2. `begin_frame` waits the current frame-slot fence, acquires an image, and waits the fence associated with that image's previous submission. `Timeout`, `OutOfDate`, and `Pending` are nonfatal scheduling outcomes with distinct recovery actions.
3. Create one `VulkanSwapchainFramebuffer` per swapchain image for a compatible single-color render pass. Record the framebuffer corresponding to `FrameTicket::image_index()` with `begin_swapchain_render_pass`; the executable command buffer is tagged with the exact swapchain generation and image index.
4. `FrameTicket::submit_and_present` rejects command buffers targeting another image or swapchain, waits on the frame-slot acquire semaphore, signals the acquired image's presentation semaphore, and advances the ring only after successful queue submission.
5. Wait or drop returned submission guards before reusing their frame slots. Recreate on acquire/present `OutOfDate` or `suboptimal`; the scheduler does not own the application event loop or automatically recreate swapchains.
6. Do not discard an acquired ticket and then replace its swapchain. If a ticket is dropped before submission, the scheduler retains that acquisition so it can be resumed against the same swapchain; a changed swapchain identity is rejected rather than silently reusing the signaled acquire semaphore.

## Not implemented yet

- Higher-level application frame policy: redraw throttling, pause/resume behavior, and integration of minimized-window events with the scheduler. The low-level scheduler reports zero-extent and out-of-date conditions but does not own the platform event loop.
- Swapchain-backed framebuffer helpers for depth attachments, multisample color/depth targets, and multi-attachment render passes.
- Explicit queue-family ownership transfers. Buffer-image copy metadata covers the supported compressed and depth/stencil formats. Resource retirement through the safe command API is fence-scoped; raw Vulkan submissions remain the caller's synchronization responsibility.
- Physical-GPU presentation tests and hardware-specific validation. A dedicated Ubuntu 24.04 Mesa lavapipe job performs deterministic offscreen graphics-pipeline rendering, buffer upload, triangle drawing, two same-type pooled readback buffers, image copy/readback comparison, pixel assertions, and fails on Vulkan validation errors; software Vulkan is not a substitute for physical-GPU testing.

## Platform notes

The engine targets Vulkan portability, not a hard-coded macOS translation layer. The available Vulkan-on-Metal implementation is provided by the system's installed SDK/driver. Khronos currently recommends KosmicKrisp on Apple Silicon and notes MoltenVK for Intel Macs and compatibility use. Platform support is not considered validated until the corresponding CI and hardware checks pass.

## Validation

The normal CI matrix must run formatting, Clippy with warnings denied, workspace tests, and documentation on Ubuntu 24.04, Windows, and macOS. Runtime Vulkan initialization and GPU-backed tests require runners with a working Vulkan loader, suitable driver, and validation layers; compile-only CI does not prove those runtime capabilities.
